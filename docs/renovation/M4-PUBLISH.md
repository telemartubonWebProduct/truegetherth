# M4 — เผยแพร่ ประวัติ และย้อนกลับ

วันที่ 2 ตุลาคม 2026 · ตามแผนที่เจ้าของอนุมัติใน [R4-M4-M5-PROPOSAL.md](R4-M4-M5-PROPOSAL.md): ร่างจาก Mirror editor ขึ้นหน้าเว็บจริงได้ด้วยปุ่มเผยแพร่ หลังดูความต่าง ทุกครั้งเก็บเป็นฉบับ (release) ที่ย้อนกลับได้ และหน้าเว็บจริงอ่านฉบับที่เผยแพร่จาก Supabase แทน `src/content`

## สิ่งที่ได้

- **เผยแพร่** (`/admin/publish`, ปุ่ม "เผยแพร่…" บนแถบ editor และเมนูหลังบ้าน): รายการร่างทุกเอกสารเทียบกับหน้าเว็บที่แสดงอยู่ (เพิ่มใหม่/ลบออก/แก้ไข และชื่อช่องที่เปลี่ยนเป็นภาษาไทย เช่น "คำถามที่พบบ่อย › หัวเรื่อง › ไทย"), ร่างที่เผยแพร่ไม่ได้ (เช่น อ้างแพ็กเกจที่ซ่อน) แยกไว้และคงเป็นร่าง, ช่องบันทึกสั้นๆ แล้วปุ่ม "เผยแพร่ N เอกสาร" — เผยแพร่เฉพาะร่างที่เห็น ณ revision ที่เห็น ถ้ามีคนเผยแพร่หรือแก้ร่างหลังจากเปิดหน้านี้ ระบบปฏิเสธและให้โหลดใหม่
- **ประวัติการเผยแพร่** (`/admin/releases`): ทุกฉบับ (เลข, เผยแพร่/ย้อนกลับจากฉบับใด, เวลา, อีเมลผู้เผยแพร่, บันทึก) ฉบับที่แสดงอยู่มีป้าย "แสดงอยู่", ปุ่ม "ต่างจากที่แสดงอยู่อย่างไร" และ "ย้อนกลับไปฉบับที่ N" (ยืนยันก่อน) การย้อนกลับสร้างฉบับใหม่ที่เนื้อหาเท่าฉบับเก่า ประวัติไม่ถูกเขียนทับ ร่างที่ค้างอยู่ไม่ถูกแตะ
- **หน้าเว็บจริงอ่านฉบับที่เผยแพร่** (`src/lib/content/published.ts`): ทุกหน้า หน้ารายละเอียดแพ็กเกจ sitemap และ metadata อ่านเนื้อหาจาก `published_content()` ด้วย publishable key ผ่าน fetch ที่ cache ไว้ด้วย tag `content`; ถ้ายังไม่เคยเผยแพร่ ไม่ได้ตั้งค่า Supabase ติดต่อไม่ได้ หรือฉบับไม่เข้ากับเว็บรุ่นนี้ (schema version/ข้อมูลไม่ผ่านการตรวจ) ใช้ `src/content` แทนและบันทึก log
- **รีเฟรชทันที**: เผยแพร่/ย้อนกลับเรียก `updateTag("content")` คำขอถัดไปได้ฉบับใหม่ (ไม่เสิร์ฟของเก่า) ตรวจแล้วจาก URL สาธารณะในเทสต์
- editor และตัวอย่างใช้ฉบับที่เผยแพร่เป็นฐานของร่าง
- แพ็กเกจที่เพิ่มในหลังบ้านแล้วเผยแพร่ ได้หน้ารายละเอียดเมื่อมีคนเปิดครั้งแรก (`dynamicParams = true`)

## ฐานข้อมูล

migration `supabase/migrations/20261002090000_content_releases.sql` + pgTAP `supabase/tests/database/content_releases.test.sql` (22 ข้อ):

- `content_releases` (snapshot เนื้อหาทั้งเว็บต่อฉบับ: หน้า ตั้งค่า แพ็กเกจ รูป ธีม; แก้ไม่ได้) และ `content_publication` (แถวเดียวชี้ฉบับที่แสดง) เปิด RLS: active Admin อ่านประวัติ/เพิ่มฉบับ/ย้าย pointer; ผู้ชมอ่านได้เฉพาะฉบับที่เผยแพร่ผ่าน `published_content()` (SECURITY DEFINER)
- `publish_content` / `rollback_content` (SECURITY INVOKER) ทำใน transaction เดียว: ล็อก, ตรวจว่าฉบับที่แสดงยังเป็นฉบับที่ Admin ดู (ไม่ใช่ → PT409), เพิ่มฉบับ, ย้าย pointer, ลบร่างที่เผยแพร่แล้ว (เฉพาะ revision ที่เห็น), บันทึก `audit_log` (`content.publish` / `content.rollback`)
- **เจ้าของต้อง apply migration นี้ (และของ M3, R4) ที่ dev project** ด้วย `npm run db:push:dev` แล้ว `npm run db:push:dev:apply`

## ทดสอบ

- E2E `tests/e2e/admin-publish.spec.ts` (local Supabase): เผยแพร่ร่าง 3 เอกสาร (ข้อความ FAQ, ราคาแพ็กเกจ, สีแบรนด์, รูปการ์ด) แล้วหน้าแรกและหน้าแพ็กเกจแสดงค่าใหม่ทันที ประวัติแสดงผู้เผยแพร่/บันทึก ร่างถูกลบ และมี audit; เผยแพร่ฉบับที่สองแล้วย้อนกลับไปฉบับแรก ข้อความ ราคา สี และรูปกลับเป็นของฉบับแรกครบ และไม่มีค่าของฉบับที่สองเหลือ; จบด้วยการเอาเนื้อหาตั้งต้นกลับขึ้นเว็บ
- Unit `tests/unit/releases.test.ts`: รายการสิ่งที่จะเปลี่ยน (แก้/เพิ่ม/ลบ, ร่างที่ใช้ไม่ได้แยกไว้), เทียบสองฉบับ, ฉบับที่เว็บรุ่นนี้แสดงไม่ได้ถูกกันไว้
- ทั้งชุด: unit 140, pgTAP 119, Playwright 139 ผ่าน + 3 ข้ามตามออกแบบ

## สิ่งที่พบระหว่างทำ

- `unstable_cache` ไม่ถูกล้างด้วย `updateTag` (Next 16 ล้างเฉพาะ fetch `next.tags` และ `cacheTag`) หน้าถูกสร้างใหม่แต่ยังอ่านค่าเดิม จึงเปลี่ยนเป็น GET fetch ที่ติด tag
- `dynamicParams = false` ใน layout `[locale]` ทำให้ Next 16.3.7 สร้างหน้าที่หมดอายุใหม่ไม่ได้ (`NoFallbackError`) และเสิร์ฟของเก่าตลอด จึงเปลี่ยนเป็น `true` (ภาษาอื่นยังเป็น 404 ใน `pageLocale()`)

## ข้อจำกัดและงานต่อ

- ยังไม่มีการตั้งเวลาเผยแพร่ (optional ตามแผน)
- production (Vercel) จะอ่านฉบับที่เผยแพร่ก็ต่อเมื่อตั้งค่า Supabase ของ production แล้ว และ migration ถูก apply ที่ project ที่ production ใช้ (M6) — ระหว่างนี้หน้าเว็บจริงยังแสดง `src/content`
- บน Vercel การรีเฟรชหลังเผยแพร่ใช้ Data Cache/ISR ของ Vercel (`updateTag` รองรับ) ต้องตรวจซ้ำบน preview deployment จริง

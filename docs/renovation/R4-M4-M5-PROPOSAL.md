# ข้อเสนอก่อนลงมือ: R4 (CRUD + อัปโหลดรูป), M4 (เผยแพร่/ประวัติ/ย้อนกลับ), M5 (ฟอร์มติดต่อกลับ + GA4)

วันที่ 1 ตุลาคม 2026 · ตาม prompt 8–10: R4 ให้เสนอ data model ก่อน, M4 ให้เสนอแผนก่อน, M5 ให้ถามเรื่อง GA4 property ช่องทางแจ้งเตือน และระยะเวลาเก็บข้อมูลก่อนเริ่ม เอกสารนี้ยังไม่ใช่ migration

## สภาพตอนนี้

- เนื้อหาที่เผยแพร่อยู่ใน `src/content` (โค้ด) และตรวจด้วย zod ตอน build
- ร่างของ Admin อยู่ใน `content_drafts` (Supabase) หนึ่งแถวต่อเอกสาร: `site`, `page:<id>`, `package:<id>`, `media:<id>`, `benefit:<id>` พร้อม revision กันชนกัน
- หน้าแพ็กเกจกรอง/เรียง/เทียบในแอปเองแล้ว (R3) ไม่ต้องใช้ SQL กรอง

## R4 — data model ที่เสนอ (ทางเลือก A, แนะนำ)

**เก็บสินค้า/บริการเป็นเอกสาร JSON ตาม schema เดิม ต่อยอดจาก M3** แทนการแตกเป็นตารางแบบ relational

| เอกสาร | เพิ่ม/ลบ/ซ่อน/เรียง | หมายเหตุ |
| --- | --- | --- |
| `package:<id>` | สร้างใหม่ (รหัส a-z ไม่ซ้ำ), ลบ, ซ่อน (`review.status = hidden`) | ราคา/เงื่อนไขพิมพ์เองทั้งหมด ไม่มีค่าเริ่มต้นที่เป็นราคา; ลบไม่ได้ถ้ายังมีการ์ด/หน้าอ้างถึง |
| `catalog` (ใหม่) | ลำดับแพ็กเกจในแต่ละหมวด/กลุ่ม | แยกจากตัวแพ็กเกจ เพื่อเรียงใหม่ได้โดยไม่แก้แพ็กเกจ |
| `benefit:<id>` | สร้าง/ลบ/แก้ชื่อและไอคอน | ลบไม่ได้ถ้าแพ็กเกจยังใช้ |
| โปร (`page:home` › promos), บริการโซลาร์ (`page:solar`) | เพิ่ม/ลบ/เรียงการ์ด แท็บ แพ็กเกจโซลาร์ | ผ่านการแก้รายการในหน้า |
| `media:<id>` | อัปโหลดรูปใหม่, แก้ alt, ลบรูปที่ไม่มีใครใช้ | ไฟล์อยู่ Supabase Storage |

รายการในหน้า (FAQ, เมนู, การ์ด, ขั้นตอน, ฉากหนัง 1–4, แท็บโปร, ลิงก์ footer): editor เพิ่ม/ลบ/เรียงได้ภายในขอบเขตที่ schema กำหนด (เช่น ฉากหนัง 1–4, แท็บโปร 1–4, การ์ด 1–8) รายการใหม่ได้ id อัตโนมัติจากชื่อ

**อัปโหลดรูป**: bucket `media` ใน Supabase Storage อ่านได้สาธารณะ เขียน/ลบได้เฉพาะ active Admin (RLS บน `storage.objects`); ชื่อไฟล์เป็น UUID ไม่ทับไฟล์เดิม (ฉบับเก่าที่ release อ้างถึงยังเปิดได้เสมอ); ตรวจชนิด (JPEG/PNG/WebP/AVIF, SVG ไม่รับ) ขนาด (ไม่เกิน 5 MB) และอ่านกว้าง×สูงจากไฟล์จริงฝั่ง server; `next/image` อนุญาตโดเมน storage ของ project

**ทางเลือก B (ไม่แนะนำตอนนี้)**: ตาราง `packages`, `package_benefits`, `categories` แบบ relational ตาม ARCHITECTURE.md §5 — ได้ query/รายงานด้วย SQL แต่ต้องเขียนการ snapshot ตอนเผยแพร่และการย้อนกลับเพิ่มอีกชั้น และ editor/หน้าเว็บต้องแปลงไปมากับ schema เดิม เพิ่มงานโดยหน้าเว็บไม่ได้อะไรเพิ่ม (กรองในแอปอยู่แล้ว) ทำภายหลังได้ถ้าต้องรายงานยอดขายตามแพ็กเกจจาก SQL

## M4 — แผนเผยแพร่ ประวัติ ย้อนกลับ

ตารางใหม่ (migration + RLS + pgTAP):

- `content_releases`: เลขรุ่น, `content` (เนื้อหาทั้งเว็บที่ผ่านการตรวจ เก็บเป็น snapshot เต็ม รวมแพ็กเกจ/รูป/ธีม), `schema_version`, ผู้เผยแพร่, เวลา, หมายเหตุ, ชนิด (เผยแพร่/ย้อนกลับจากรุ่น N) — แก้/ลบไม่ได้
- `content_publication`: แถวเดียวชี้รุ่นที่เผยแพร่อยู่
- อ่านได้: ทุกคน (anon) อ่านเฉพาะรุ่นที่เผยแพร่อยู่; Admin อ่านทุกรุ่น

ขั้นตอน:

1. **ดูก่อนเผยแพร่**: หน้า `/admin/publish` แสดง diff ระหว่างฉบับเผยแพร่กับร่างทั้งหมด (ใช้ `diffPaths`/`pathLabel` ที่มีอยู่) แยกตามเอกสาร พร้อมผลตรวจ schema/reference
2. **เผยแพร่**: Server Action รวมร่างเข้าฉบับเผยแพร่ ตรวจด้วย zod + `contentProblems` แล้วเรียก function `publish_release(content, based_on, note)` ใน transaction เดียว: สร้างรุ่น, ย้าย pointer, ลบร่างที่เผยแพร่แล้ว (เฉพาะ revision ที่ดู diff), บันทึก `audit_log` ถ้ามีคนเผยแพร่ซ้อน (based_on ไม่ใช่รุ่นล่าสุด) ปฏิเสธ
3. **หน้าเว็บอ่านจาก Supabase**: `getPublishedContent()` แบบ `'use cache'` + `cacheTag('content')` อ่านรุ่นที่เผยแพร่; ถ้า Supabase ไม่ได้ตั้งค่า/ติดต่อไม่ได้/ยังไม่มีรุ่น/ข้อมูลไม่ผ่าน schema → ใช้ `src/content` (fallback) หน้าเว็บยังเป็น static + revalidate ตาม tag
4. **รีเฟรช**: เผยแพร่/ย้อนกลับแล้วเรียก `updateTag('content')` ใน Server Action (คำขอถัดไปได้ฉบับใหม่ทันที ไม่ใช่ stale) แล้วตรวจจาก public URL ในเทสต์
5. **ประวัติและย้อนกลับ**: หน้า `/admin/releases` รายการรุ่น (ใคร เมื่อไร หมายเหตุ) ดู diff ระหว่างรุ่น ย้อนกลับ = สร้างรุ่นใหม่ที่มีเนื้อหาเท่ารุ่นเก่า (ไม่ลบประวัติ) คืนข้อความ/ราคา/ธีม/รูปครบเพราะ snapshot เก็บทั้งหมดและไฟล์รูปไม่ถูกทับ
6. **รุ่นแรก**: ครั้งแรกที่เผยแพร่ ฐานคือ `src/content` ปัจจุบัน

E2E (local Supabase): เผยแพร่แล้วหน้าเว็บเปลี่ยน, ย้อนกลับแล้วข้อความ/ราคา/ธีม/รูปกลับครบ, ผู้ไม่ใช่ Admin เผยแพร่ไม่ได้ (RLS), เผยแพร่ซ้อนถูกปฏิเสธ, Supabase ล่ม → fallback

ผลต่อ production: Vercel production ยังไม่มีค่า Supabase จึงยังใช้ `src/content` ต่อไปจนกว่าจะตั้งค่า (ไม่พัง) และเมื่อเปิดใช้ ต้องตัดสินว่า production ใช้ Supabase project ไหน (M6)

## M5 — สิ่งที่ต้องถามก่อนเริ่ม

1. **GA4 property**: มีอยู่แล้วไหม (Measurement ID `G-…` และสิทธิอ่าน property สำหรับรายงาน) หรือให้ทำระบบไว้แบบปิดและเปิดเมื่อมี
2. **ช่องทางแจ้งเตือนทีมขายเมื่อมีคำขอ**: อีเมล (ต้องมีบัญชีส่ง SMTP/บริการส่งอีเมล), LINE Official Account (Messaging API ต้องมี channel token — LINE Notify ปิดบริการแล้ว), หรือดูในหลังบ้านอย่างเดียว
3. **ระยะเวลาเก็บข้อมูลผู้ติดต่อ** (PDPA): เช่น 6 เดือน / 1 ปี / 2 ปี หลังปิดคำขอ แล้วลบหรือทำให้ระบุตัวตนไม่ได้อัตโนมัติ

ค่าที่เสนอระหว่างรอ: ฟอร์ม ชื่อ, เบอร์โทร, จังหวัด, บริการ/แพ็กเกจที่สนใจ, เวลาสะดวก, หมายเหตุ, ยินยอมตามนโยบาย; กันสแปมด้วย honeypot + จำกัดอัตราต่อ IP + Turnstile ถ้าเลือก; กันส่งซ้ำด้วย idempotency key; consent คุกกี้แบบปฏิเสธเป็นค่าเริ่มต้น (Google Ads/GA4/Tawk โหลดหลังยินยอม — **มีผลกับ conversion ที่เพิ่งคืนใน prompt 1**: ถ้าผู้ชมไม่ยินยอม จะไม่ยิง)
